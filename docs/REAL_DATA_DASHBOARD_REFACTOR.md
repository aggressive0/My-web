# REAL_DATA_DASHBOARD_REFACTOR.md

> 面向 Agent 的实施规格。目标：将「总览」与「流失分析」从混合演示数据的展示页，改造成以 Steam 公开数据为证据、口径透明、可追溯、可降级的运营分析页面。
>
> 适用仓库：aggressive0/liusheng-player-retention  
> 当前基线：main 分支静态前端 `front/static_html/`，远端数据位于 `data` 分支。  
> 本文只定义重构方案，不代表所有接口或数据字段已经在当前版本实现。实施时必须先对照实际 JSON 样本与代码，不得臆造字段。

## 0. Agent 执行规则

### 0.1 目标与非目标

**必须完成**
- 清除总览、流失分析页面中未标识的模拟数值与模拟业务结论。
- 复用现有 `RealData` 数据加载层，形成唯一、可测试的数据入口。
- 优先消费现有 `data` 分支文件，不为已有数据重复造接口。
- 为每个真实指标显示数据来源、更新时间、统计窗口、样本量或覆盖率。
- 对缺失、低样本、过期、部分可用数据显示明确状态；不以 0 或 mock 值填充。
- 保留现有深色空间科技视觉、总览中心地球与页面整体信息架构，重点调整数据语义和模块内容。
- 让游戏选择器在总览和流失分析中保持一致，并确保同一筛选条件驱动相关图表。

**本期不做**
- 不伪造账号级 DAU、MAU、D1/D7/D30 留存、真实流失人数、真实付费/LTV、真实召回成功率。
- 不把 Steam 成就完成率当作 cohort 留存率。
- 不把语言市场坐标解释成玩家真实所在地。
- 不把 Steam 的 voted_up 投票标签与模型预测结果混为一谈。
- 不为了视觉填满页面而制造无数据的地图热点、预警、趋势线或预测数字。
- 不在前端直接暴露第三方模型密钥或 Steam 私密凭据。

### 0.2 实施前必须核对的仓库事实

当前代码审阅发现以下风险，开始改 UI 前先处理：

1. `front/static_html/js/realdata.js` 的 REMOTE 仍指向旧仓库 `aggressive0/My-web`。新仓库数据已经迁移至 `aggressive0/liusheng-player-retention` 的 `data` 分支。确认采集工作流确实发布到新仓库后，将远端地址改为：
   ```js
   var REMOTE = 'https://raw.githubusercontent.com/aggressive0/liusheng-player-retention/data/';
   ```
   若生产数据源仍由旧仓库维护，则不要盲目改地址；先检查两个仓库的采集工作流、最新提交和文件内容，并在本文件的实施记录中说明最终数据源。

2. `front/static_html/js/dashboard-data.js` 文件头明确声明为 Mock，内部仍包含硬编码 KPI、区域、玩家点位、热点、迁移弧线、风险人数、召回率和留存 cohort。总览页面若继续调用这些方法，就会出现「部分真实、部分 mock」混合口径。

3. `index.html` 和 `analysis.html` 的 HTML 注释、底部口径说明与 README 存在历史遗留描述。需同步更新，不能只改屏幕上可见的数字。

4. `analysis.html` 已经使用 `RealData.load()` 读取情感、成就、主题数据，但顶部 KPI 和玩家分群仍是演示内容。当前情感图表将不同游戏的日数据合并，必须增加游戏筛选或明确标为全样本汇总，不能在用户选择单款游戏时仍显示跨游戏聚合值。

5. `RealData.load()` 当前缓存按文件名缓存结果，没有按筛选条件缓存的需求；同一数据文件加载后在页面生命周期内复用即可。不要把游戏筛选逻辑塞进网络层。

6. 页面中存在 `实时` 字样，但 GitHub Raw 的 data 分支是批次发布快照，不是实时流。统一用 `LIVE DATA`（远端最新发布数据）与 `SNAPSHOT`（仓库内静态快照）区分来源，并展示更新时间；文案不得暗示秒级实时。

## 1. 产品信息架构与统一口径

### 1.1 产品定位

两个页面共同讲清楚一条链路：

**公开玩家反馈 → 玩家反馈变化 → 游戏级风险信号 → 可执行运营判断**

- 总览：回答「当前哪些游戏值得关注？变化来自哪里？有什么证据？」
- 流失分析：回答「某款游戏的玩家反馈正在发生什么变化？哪些主题/时长层级更值得关注？判断依据是什么？」

公开数据只能形成「游戏级公开信号研判」，不能直接识别具体玩家是否流失。所有页面标题、指标、AI 文案都必须遵守这一边界。

### 1.2 指标命名规范

| 数据 / 指标 | 推荐展示名 | 禁止或不推荐的名称 | 解释 |
|---|---|---|---|
| Steam 当前在线人数 | 当前同时在线（CCU） | 活跃玩家、DAU | 某时刻同时在线，不是日活 |
| 多款游戏 CCU | 样本游戏当前同时在线合计 | 平台总活跃玩家 | 仅是当前纳入样本的游戏之和 |
| Steam voted_up | Steam 推荐率 / 不推荐率 | 模型正面率 / 情感得分 | 用户在 Steam 的实际投票信号 |
| 模型分类输出 | 模型推荐倾向（正/中/负） | 玩家真实情绪、真实满意度 | 基于弱标签训练的模型估计 |
| 主题词典命中 | 主题候选信号 | 已确认流失原因 | 关键词规则，不等同语义因果分析 |
| Steam 全局成就完成率 | 全局成就解锁率 | 玩家留存率、流失漏斗 | 全体统计快照，不是 cohort |
| risk-daily | 游戏级公开信号风险指数 | 流失概率、流失率 | 自定义综合指数，不是概率 |
| 评论 playtime 分层 | 评论者游戏时长分层 | 全体玩家生命周期分群 | 只代表评论样本 |
| globe-daily 坐标 | 语言市场代表点 | 玩家真实位置、流失区域 | 点位为语言市场可视化锚点 |

### 1.3 每个数据面板的通用来源条

每个真实数据模块必须具备一个来源条（可复用 `css/realdata.css`）：

- 来源标记：`LIVE DATA` / `SNAPSHOT` / `UNAVAILABLE`
- 数据更新时间：优先使用数据文件 `updated_at`，其次使用记录级更新时间。
- 数据口径：例如「Steam 用户评论 · 最近采集样本」。
- 样本量：n 条评论、n 个市场点、n 个采样点等。
- 覆盖情况：日期范围、主题匹配覆盖率、可用游戏数。
- 过期状态：按数据类型设置阈值，过期时展示「数据可能过期」，但仍可显示最后一次有效数据。

禁止把远端文件读取成功等同于数据新鲜。远端 JSON 可能是旧快照。

### 1.4 数据状态模型

统一使用以下状态，不允许各模块私自发明语义：

| 状态 | 含义 | UI 表现 |
|---|---|---|
| loading | 正在读取 | 骨架屏或轻量加载提示 |
| ready | 数据结构有效且满足展示要求 | 正常图表 |
| low_sample | 有数据，但样本量不足以支持稳定结论 | 图表可展示，黄色提示，禁止强结论 |
| partial | 部分游戏/日期/指标可用 | 展示可用部分，并列出缺失项 |
| empty | 数据文件有效，但筛选条件下没有记录 | 空状态，说明筛选范围 |
| unavailable | 远端与快照均不可用 | 明确不可用，不绘制虚构值 |
| error | JSON 解析失败或结构不符合契约 | 错误提示，保留错误诊断信息 |

建议建立通用判断函数：
- `hasRows(rows)`
- `isFresh(updatedAt, maxAgeHours)`
- `sampleStatus(n, minN)`
- `safeRate(numerator, denominator)`

所有除法必须先判断分母；分母为 0 返回 null，不返回 0%。

### 1.5 时间窗口原则

- 不能固定显示近 7/30/90 天，除非数据实际覆盖相应日期。
- 图表可选范围由当前筛选数据的真实日期覆盖决定。
- CCU 当前数据窗口约为滚动 72 小时；不要把它画成 30/90 天。
- sentiment、topics、risk 的历史覆盖因游戏而异；选择游戏后重新计算可用范围。
- 日期缺口必须保留，不可补 0、线性插值或平滑成连续趋势。
- 日级趋势使用自然日；CCU 使用真实时间戳。
- 页面应显示「数据覆盖：YYYY-MM-DD 至 YYYY-MM-DD」，而不只是「近 30 天」。

## 2. 数据源与字段契约

### 2.1 当前可消费的数据文件

数据文件位于仓库 `data` 分支根目录，前端通过 `RealData.load(fileName)` 读取。

| 文件 | 用途 | 可用字段（以实际 JSON 为准） | 注意事项 |
|---|---|---|---|
| `collection-status.json` | 采集任务状态、新鲜度 | `updated_at`、各任务/游戏的状态、fetched、时间戳 | 先核对具体嵌套结构，不可猜字段路径 |
| `steam-ccu.json` | CCU 时序、窗口摘要 | 游戏注册表、appid、name、series、timestamp、players、latest/high/low/mean/count | 当前在线不是 DAU；时间点不等间隔 |
| `steam-funnels.json` | 全局成就解锁率 | 游戏、achievements、achievement name、percentage、span/first/last（若发布） | 快照型全局比例，不是用户 cohort |
| `reviews-daily.json` | 评论量、投票、时长分层 | 游戏、days、date、n、positive/negative、language、playtime buckets | 各游戏覆盖不一致 |
| `reviews-samples.jsonl` | 真实评论证据 | review_id、appid、review、voted_up、language、timestamp、playtime_at_review 等 | 逐行 JSON；需分页/按需读取，注意 XSS |
| `sentiment-daily.json` | 模型推荐倾向趋势 | games、days、date、n、pos、neg、neu、actual_up、low_conf、mean_p、low_conf_share、totals | 模型输出与实际投票必须分开展示 |
| `topics-daily.json` | 主题候选信号 | games、n_reviews、coverage、topics、label、count、share、trend、sample_ids | 关键词命中；一条评论可命中多个主题 |
| `risk-daily.json` | 游戏级公开信号风险 | games、score、status、components_used、weights_applied、components、date | 缺失分量不当 0；不是流失概率 |
| `globe-daily.json` | 语言市场地图 | language、market、latitude、longitude、review_count、positive_rate、negative_rate、top_topic、risk_score | 坐标是语言市场代表点，不是玩家所在地 |

字段名和嵌套层级以 `data` 分支实际文件为准。若发现文件结构与本表不一致，先修改数据适配器并添加 fixture 测试，再改组件。

### 2.2 建议前端统一的内部数据模型

不要让 HTML 图表直接消费原始 JSON。通过 `dashboard-data.js`（或新增 `dashboard-realdata.js`）输出规范化 view model：

```js
{
  meta: {
    source: 'remote' | 'snapshot',
    updatedAt: 'ISO-8601',
    generatedAt: 'ISO-8601',
    coverageStart: 'YYYY-MM-DD' | null,
    coverageEnd: 'YYYY-MM-DD' | null,
    sampleSize: 0,
    status: 'ready' | 'low_sample' | 'partial' | 'empty' | 'unavailable',
    notes: []
  },
  filters: {
    appid: 'all' | '1203220',
    range: 'available' | '7d' | '30d'
  },
  data: {}
}
```

要求：
- 原始字段名保留在 adapter 内，组件只读统一字段。
- 数值缺失用 `null`，绝不以 0 替代未知。
- 百分比统一用 0–100 数值，比例统一命名为 `RatePct`。
- 时间统一为 ISO 字符串或 epoch 毫秒，图表层再格式化。
- 每个指标可追溯到来源文件和计算口径。
- 不得把来自不同日期、不同样本集的数据强行拼成一条同口径曲线。

### 2.3 游戏注册表

以 `steam-ccu.json` 或仓库已有游戏配置为游戏列表主来源，避免前端硬编码第二份游戏列表。

标准字段：
- `appid`：Steam App ID，字符串或数字统一转换成字符串。
- `name`：游戏名称。
- `color`：展示颜色（仅视觉配置，不参与计算）。
- `enabled`：是否参与默认展示。
- `availableMetrics`：可选，由 adapter 根据数据实际覆盖动态生成。

所有文件按 appid 关联，不要只按游戏名称关联。名称可能调整、存在大小写或别名差异。

## 3. 总览页（index.html）重构规格

### 3.1 页面目标与布局

保留当前「顶部 KPI + 左右数据舱 + 中央地球 + 底部决策链」结构。内容从模拟的玩家运营后台，调整为公开数据监测中枢。

建议结构：

1. 顶部：4 张公开数据 KPI。
2. 左上：多游戏 CCU 趋势。
3. 左下：游戏舆情与风险排行。
4. 中央：语言市场舆情地球。
5. 右上：情感信号对照。
6. 右中：规则驱动的风险预警。
7. 右下：AI 运营决策建议（无真实召回结果时只给建议，不报效果）。
8. 底部：热点主题 → 玩家反馈 → 风险信号 → 运营建议。

### 3.2 顶部 KPI（4 张）

| KPI | 数据来源 | 计算规则 | 展示单位 | 边界 |
|---|---|---|---|---|
| 样本游戏当前同时在线 | steam-ccu | 对每款游戏取最新有效采样值后求和 | 人 | 标注「样本游戏合计」，不是 Steam 全平台 DAU |
| Steam 不推荐率 | reviews-daily 或 sentiment actual_up | `negative / (positive + negative) * 100`，按选定窗口汇总 | % | 仅统计当前评论样本；必须展示 n |
| 模型负面倾向率 | sentiment-daily | `neg / n * 100`，按 n 加权聚合 | % | 模型弱标签结果；必须与 Steam 投票分开展示 |
| 最高可用风险指数 | risk-daily | 只在 status 可用时取最高 score | /100 | 需显示对应游戏与 status；若无可用项显示「暂无足够数据」 |

实现要求：
- 默认「全部样本游戏」时，CCU 合计只对最新采样时间合理接近的游戏求和。若时间差超过设定容忍窗口（建议 2 小时），标记为「非同步采样合计」并展示参与数。
- 评论比例必须按总数加权，不得简单平均各游戏百分比。
- 不推荐率与模型负面倾向率必须是两张不同 KPI 或在同一 KPI 内用双值明确区分，不可互相替代。
- 最高风险指数只在 status 为 `ok` 或项目定义的可展示状态时参与排序；`insufficient` 排除，`low_sample` 单独标识。
- 不展示环比 sparkline，除非数据文件有足够且同口径的历史点。
- 每张 KPI 下方显示短说明：来源、更新时间、n 或参与游戏数。

### 3.3 左上：多游戏在线人数趋势

将旧「玩家活跃趋势」改名为「多游戏在线人数趋势（CCU）」。

数据：
- `steam-ccu.json`
- 使用真实 timestamp 和 players。
- 多游戏曲线默认按游戏分色；提供单款游戏筛选。
- 默认展示原始在线人数；可切换「指数化对比」以观察各游戏相对自身窗口均值的变化。

指数化公式：
```
index(t) = players(t) / mean(players_in_selected_window) * 100
```
仅用于节奏对比，不能用于比较不同游戏的绝对人数。

图表配置：
- ECharts line。
- xAxis: `time`，使用真实时间戳，不等间隔类目轴。
- yAxis: 原始人数时标注「同时在线人数」；指数模式标注「相对窗口均值指数（100=均值）」。
- 不平滑，不跨采样缺口补线（使用 null 或分段数据）。
- tooltip 展示游戏名、时间、CCU、相对变化（若可算）。
- 图例支持单游戏显隐。
- 面板头部显示窗口起止时间、采样点数、最后更新时间。

空状态：
- 没有可用 CCU：显示「当前没有可用在线人数采样」。
- 某游戏点数不足：从曲线中排除并列出原因，不生成水平 0 线。

### 3.4 左下：游戏舆情与风险排行

替换原「区域排行」或模拟风险地区排行。

每行字段：
- 游戏名称；
- 评论样本量 n；
- Steam 不推荐率；
- 模型负面倾向率；
- 风险指数 /100；
- 当前主要主题；
- 数据状态（正常 / 低样本 / 数据不足）。

排序规则：
1. 先按数据充分性：`ok` → `low_sample` → `insufficient`。
2. 在同一状态内按风险指数降序。
3. 不可用风险值不参与数值排序。
4. 不以评论量直接推断风险高低。

交互：
- 点击游戏行，更新总览页面的游戏筛选；
- 地球只高亮该游戏对应语言市场点；
- CCU、情感、主题、风险卡同步切换；
- 「全部游戏」可恢复总览。

### 3.5 中央地球：语言市场舆情分布

保留 `globe-stage.js` 与 globe.gl 的三维舞台。地球数据必须改为 `globe-daily.json`。

点位字段：
- `language` / `market`
- `latitude` / `longitude`
- `review_count`
- `positive_rate` / `negative_rate`
- `top_topic`
- `risk_score`

点位语义：
- 每个点代表「某语言评论样本市场的代表坐标」。
- 不代表玩家真实位置，不代表流失用户地理分布。
- 不得使用「北美高危玩家 3.2 万」「流失迁移路径」等没有账号级证据的标注。

视觉编码建议：
- 点大小：评论样本量（设置上限，避免大点遮挡）。
- 点颜色：风险等级或负面率分档，二者只能选一个主编码；另一个放 tooltip。
- 光环：只用于选中状态，不代表新增玩家或风险人数。
- 不绘制迁移弧线，除非未来确有玩家迁移/跨区账号级数据。

交互：
- 点击点位打开侧边信息卡：
  - 市场/语言；
  - 评论数；
  - Steam 推荐率/不推荐率；
  - 主要主题候选；
  - 风险分数与状态；
  - 数据更新时间。
- 点击市场点联动右侧情感/主题信息时，必须确认对应数据粒度支持该语言过滤；若不支持，明确提示「当前情感模型数据未按语言拆分」。
- 缺少有效坐标时不绘制点位，但在数据诊断中统计被跳过的点。

### 3.6 右上：情感信号对照

命名为「玩家反馈信号」，不要只叫情绪监测。

推荐同一面板展示两组独立序列：
- Steam 实际推荐率：`actual_up / (actual_up + actual_down)`（若数据契约提供实际计数）；
- 模型正面倾向率：`pos / n`；
- 模型负面倾向率：`neg / n`；
- 每日样本量 n；
- 低置信度比例 `low_conf_share`。

图表：
- 推荐率与模型正面倾向率用两条线对照。
- 可选以柱状/淡色面积展示每日样本量。
- tooltip 同时展示模型 n、Steam 投票样本量、低置信度率。
- 不把 `actual_up` 当模型预测，也不把 `pos` 当 Steam 推荐票。
- 当前数据仅覆盖部分游戏、日期，选择游戏后仅显示其真实时间范围。
- 对于只有 1 天数据的游戏，展示摘要而不绘制趋势。

### 3.7 右中：规则驱动风险预警

当前演示预警全部替换为由真实数据计算的事件。每条预警必须有：
- `id`（稳定 hash 或规则+appid+date）；
- `appid` / `gameName`；
- `level`；
- `triggeredAt`；
- `ruleId`；
- `title`；
- `evidence[]`；
- `status`；
- `suggestedAction`。

第一版规则只做可解释规则，不做无依据的 LLM 自由预警：

| 规则 ID | 触发条件建议 | 最低数据要求 | 展示文案 |
|---|---|---|---|
| NEGATIVE_SPIKE | 当日模型负面倾向率较前 7 日基线增加 ≥10pp | 当日 n≥30，基线至少 3 个有效日 | 模型负面倾向上升 |
| TOPIC_SURGE | 某主题近 7 日占比较前 7 日上升 ≥8pp | 两个窗口各自有效评论量达到阈值，coverage 达标 | 某主题讨论热度上升 |
| CCU_DROP | 最近有效 CCU 均值较前一窗口下降 ≥20% | 两个窗口各至少 3 个采样点 | 在线人数出现明显回落 |
| RISK_HIGH | risk score 达项目配置阈值且 status 可用 | 至少有足够分量，且样本量满足要求 | 游戏级公开信号风险偏高 |

阈值必须放入配置常量，不能散落在 DOM 脚本中。默认阈值是初始产品规则，不是统计显著性证明；界面注明「规则阈值，可配置」。

重要约束：
- 没有事件时展示「当前窗口未触发预警规则」，不要填入假事件。
- 低样本事件只能作为「观察提示」，不能标为高风险。
- 同一事件跨轮采集要去重；状态变化才新增事件。
- 每条预警展开后展示规则计算值、基线、当前值、样本量、数据来源。
- 预警只说明公开信号异常，不声称识别了真实流失用户。

### 3.8 右下：AI 运营决策建议

将原来含虚构预算、预计挽回率和影响人数的「下一步最优动作」改成「AI 运营决策建议」。

输入：
- 当前游戏筛选；
- risk-daily 组件与状态；
- sentiment 变化；
- topics 热点；
- CCU 变化；
- 真实评论证据（仅抽样引用）。

输出结构：
```json
{
  "summary": "基于公开信号的简短判断",
  "priority": "high | medium | low",
  "evidence": [
    {
      "source": "sentiment-daily.json",
      "metric": "negative_rate",
      "value": 31.2,
      "baseline": 18.4,
      "unit": "%",
      "sample_size": 120
    }
  ],
  "actions": [
    {
      "title": "建议动作",
      "reason": "对应证据",
      "effort": "low | medium | high",
      "expectedOutcome": "定性预期，不填虚构百分比"
    }
  ],
  "limitations": ["当前未接入账号级召回转化数据"]
}
```

如果后端 AI 服务不可用：
- 显示「AI 服务暂不可用」；
- 可以展示基于规则的摘要，但必须标注「规则生成」；
- 不要静默回退成预设的 AI 文案。

AI 输出必须带证据引用。模型不能自行编造指标、样本量、地区或效果百分比。前端对输出做 schema 校验和文本转义。

### 3.9 底部决策链

改成四段：
1. 热点主题：来自 topics-daily；
2. 玩家反馈：来自真实评论、投票与模型分析；
3. 风险信号：来自 risk-daily 与可解释异常规则；
4. 运营建议：来自规则/AI 建议。

每一段只展示真实证据和状态，不显示虚构的影响人数、恢复率、流失人数。点击任一节点滚动或切换到对应面板。

## 4. 流失分析页（analysis.html）重构规格

### 4.1 页面目标与结构

页面以「选定游戏」为主线。顶部提供游戏选择器；所有图表必须响应同一 appid。页面结构：

1. 顶部 KPI：评论样本量、Steam 不推荐率、模型负面倾向率、游戏级公开信号风险指数。
2. 主图：评论推荐倾向趋势与样本量。
3. 次图：全局成就解锁率梯度（快照）。
4. 底部左：评论者游戏时长分层。
5. 底部右：主题候选与典型评论证据。
6. 页面底部：数据口径、覆盖日期、限制说明。

### 4.2 游戏选择器与筛选状态

- 默认选择「全部游戏」或默认样本量最大的游戏，必须在页面上明确当前模式。
- 选择单款游戏后，所有 KPI、情感趋势、成就图、时长分层、主题列表、评论证据均切换到同一 appid。
- 若某文件没有该游戏记录，对应面板显示 empty/unavailable，不得沿用上一款游戏的数据。
- 不允许情感趋势显示全部游戏汇总、而页面标题却显示单款游戏。
- 时间范围选项依据当前游戏真实覆盖范围动态生成；不可用范围禁用并显示原因。

### 4.3 顶部 KPI

| KPI | 数据 | 计算 | 备注 |
|---|---|---|---|
| 评论样本量 | reviews-daily / sentiment-daily | 选定时间窗口 n 求和 | 说明是已采集评论样本，不是游戏全部玩家 |
| Steam 不推荐率 | reviews-daily 的 positive/negative 投票计数 | negative/(positive+negative) | 投票分母不包含无法判定投票的记录 |
| 模型负面倾向率 | sentiment-daily | neg/n | 弱标签模型输出，展示低置信度比例 |
| 公开信号风险指数 | risk-daily | 读取 score 与 status | 不展示为流失概率；不足时显示状态 |

KPI 辅助信息：
- 统计窗口；
- 样本数；
- 更新时间；
- 数据状态；
- 适用限制。

若评论统计与情感模型的样本量不一致，分别展示对应 n，不得把一个 n 复用到两种指标。

### 4.4 主图：评论推荐倾向趋势

现有 `trendChart` 需要改造为按游戏过滤的数据驱动图表。

图表内容：
- 模型正面倾向率；
- 模型中性区间比例；
- 模型负面倾向率；
- Steam 实际推荐率（仅在分母可用时展示）；
- 每日评论样本量。

数据处理：
- 先按 appid 过滤；
- 再按自然日聚合；
- 以当日有效样本数为权重计算窗口摘要；
- 不足 5 条的日期默认不画趋势点，但必须在 tooltip 或数据说明中说明过滤规则；
- 不足 30 条的日期可以显示，但标记为低样本，不参与强预警；
- 缺失日期留空，不补零。

建议图表：
- 主坐标轴 0–100%；
- 推荐率和模型倾向率使用不同线型；
- 样本量使用第二坐标轴柱状图或 tooltip 辅助；
- tooltip 展示日期、各比例、n、low_conf_share；
- 图例名称必须清晰区分「Steam 实际推荐率」和「模型正面倾向率」。

注意：现有 `dailyRows()` 将所有游戏聚合到同一日期，需要改为 `dailyRows(doc, appid)`。只有 appid='all' 时才允许汇总，且要按分子/分母重新计算，不可平均各游戏比例。

### 4.5 成就解锁率梯度

将旧「成就完成漏斗」改名为「全局成就解锁率梯度」。

说明文案：
「Steam 全局成就统计快照。按成就解锁率排序，用于观察不同成就的完成门槛分布；不代表同一批玩家的流失过程，也不是 D1/D7/D30 留存。」

图表：
- x 轴：成就解锁率排序位置（0–100%）。
- y 轴：全局解锁玩家比例（0–100%）。
- 游戏切换器与主页面选择器一致。
- tooltip 展示成就名称、解锁率、appid、数据更新时间。
- 若当前快照不含成就名称，可显示序号，不得编造关卡阶段。
- 不使用「早期劝退」「流失发生在 30% 进度」等因果结论。
- 只有一个快照时不显示时间趋势。

### 4.6 评论者游戏时长分层

替换旧「玩家分群画像」（新手/成长/核心/沉默边缘等无账号证据的分群）。

数据来源：`reviews-daily.json` 中评论者 `playtime_at_review` 分桶，或从评论样本按实际字段计算。

分桶建议与采集端一致：
- 少于 1 小时；
- 1–10 小时；
- 10–50 小时；
- 50 小时及以上。

每个分桶展示：
- 评论样本数；
- 占当前游戏评论样本的比例；
- Steam 不推荐率；
- 模型负面倾向率（若有足够可关联样本）；
- 高频主题（若有对应分层主题数据）。

严禁：
- 把评论者时长分布解释成全体玩家时长分布；
- 把 50h+ 称为核心玩家，除非明确标注为「评论样本中的高时长组」；
- 把低时长评论者直接称为流失玩家；
- 用评论者占比推断玩家生命周期占比。

若目前 `reviews-daily.json` 只有桶计数，没有按桶拆分投票数据，则先展示样本量分布，不得凭空计算各桶负面率。可在后续 collector 扩展按 playtime bucket 聚合的 positive/negative 计数。

### 4.7 主题候选与热点趋势

保留现有 `topicRows`，升级为可筛选、可追溯的「玩家反馈主题候选」。

每个主题展示：
- 主题名称；
- 命中评论数；
- 占比；
- 近 7 日与前 7 日变化（若基期可用）；
- 主题覆盖率；
- 候选标签；
- 样本状态。

规则：
- coverage 必须和主题占比同时展示。
- 一条评论可以命中多个主题，因此主题 share 总和可能超过 100%，需要在图例说明。
- `base_zero` 时显示「基期无样本，暂不可比较」，不要显示无穷大或 100% 增长。
- 当前词典是关键词匹配，界面标记「关键词候选」，不声称语义识别已确认。
- 不要选评论量最大的游戏作为固定代表；必须跟随当前 appid。全部游戏视图则按分子/分母汇总后排序。

点击主题展开证据列表：
- 评论原文（适当截断，支持展开）；
- Steam 推荐/不推荐；
- 评论时间；
- 评论者游戏时长；
- 语言；
- 来源 review_id（可复制或打开 Steam 评论链接，前提是链接由可信字段构建且编码安全）。

评论文本必须使用 `textContent` 或安全模板转义，禁止直接将原始评论字符串拼进 `innerHTML`。

### 4.8 页面底部口径说明

移除现有「30 天滚动窗口｜覆盖 1.26M 活跃玩家｜流失定义：连续 14 天未登录」等无数据支撑说明。

统一显示：
- 当前游戏；
- 当前统计窗口；
- 实际覆盖日期；
- 评论样本量；
- 模型适用范围；
- 主题匹配覆盖率；
- 当前不可用指标；
- 公开数据限制说明。

## 5. 数据适配层与模块拆分

### 5.1 推荐文件结构

尽量保持现有静态站零构建形态：

```
front/static_html/
├── index.html
├── analysis.html
├── js/
│   ├── realdata.js                 # 网络/快照加载、来源和状态
│   ├── dashboard-data.js           # 逐步移除 mock，保留统一 view model API
│   ├── dashboard-adapters.js       # 原始 JSON -> 规范化数据（建议新增）
│   ├── dashboard-overview.js       # 总览页渲染与交互（建议从 inline script 拆出）
│   ├── dashboard-analysis.js       # 流失分析页渲染与交互（建议从 inline script 拆出）
│   └── globe-stage.js              # 地球渲染层，只接收已规范化数据
├── css/
│   └── realdata.css
└── json/                           # 离线快照
```

不要求一次性拆完所有 inline script；优先建立 adapter 和数据契约，再迁移脚本。

### 5.2 建议 adapter API

```js
DashboardAdapters.loadOverview()
DashboardAdapters.loadAnalysis(appid, range)
DashboardAdapters.getGameRegistry()
DashboardAdapters.getCcuSeries(appid)
DashboardAdapters.getReviewSummary(appid, range)
DashboardAdapters.getSentimentSeries(appid, range)
DashboardAdapters.getRiskSummary(appid)
DashboardAdapters.getTopicSummary(appid, range)
DashboardAdapters.getGlobeMarkets(appid)
DashboardAdapters.getAchievementSnapshot(appid)
DashboardAdapters.getPlaytimeBuckets(appid, range)
DashboardAdapters.getReviewEvidence(appid, topicId, limit)
```

以上为建议接口，不要求机械照抄。所有函数应返回 Promise 或明确同步数据结构，并包含 meta。

### 5.3 统一数据加载

`RealData.load()` 应继续负责：
1. 远端 data 分支；
2. 仓库内快照；
3. unavailable。

不得增加 mock 作为第三级回退。

改进项：
- REMOTE 地址集中配置，不在页面脚本重复写。
- fetch 设置超时；JSON 解析错误需要可诊断。
- 可选支持 `?refresh=1` 绕过页面内存缓存，便于调试。
- 缓存只缓存原始文件，不缓存 appid/range 筛选结果。
- `stamp()` 不应直接将未经转义的动态文本拼入 HTML。
- stale 阈值按文件类型配置，例如 CCU 允许 3 小时、每日情感/主题/risk 允许 36 小时；最终阈值根据采集计划核对。
- 来源显示为「远端数据文件」而非不严谨的「实时」。

### 5.4 适配器纯函数

数据处理尽可能写成纯函数，方便单元测试：
- `normalizeGameId(value)`
- `filterByAppid(rows, appid)`
- `aggregateCounts(rows)`
- `calculateRate(num, den)`
- `weightedRate(items, numeratorKey, denominatorKey)`
- `getDateCoverage(rows)`
- `getCcuCoverage(series)`
- `calculateTopicDelta(current, baseline)`
- `deriveRiskAlerts(input, config)`
- `buildOverviewKpis(data)`

纯函数必须处理：
- null / undefined；
- 空数组；
- 0 分母；
- 重复日期；
- 重复 appid；
- 无效日期；
- 缺失分量；
- 负数或超范围比例；
- 不同文件更新时间不一致。

### 5.5 风险指数的展示规则

风险计算公式当前定义为：

```
risk = 0.35*N + 0.30*G + 0.20*C + 0.15*A
```

缺失分量按剩余可用权重重归一化，但页面必须展示：
- 当前 score；
- status；
- components_used；
- 实际 weights_applied；
- 每个分量值；
- 不可用分量原因。

例如 PUBG 目前可能只有 C 分量可用，则不能将其与四个分量齐全的游戏作为同等置信度的排名结论。排序先看 status/数据充分性，再看 score。若数据契约中 status 语义发生变化，先更新统一规则并添加测试。

### 5.6 安全与隐私

- 所有评论原文、主题名、游戏名均视为外部输入。
- 动态 DOM 使用 `textContent`；必须拼 HTML 时统一 escape。
- 不将 API key、GitHub token 或模型密钥写进静态 JS。
- AI 请求走后端代理，前端只访问本项目 API。
- 日志不要记录完整用户密钥或敏感配置。
- 当前项目没有账号级玩家数据，不得为了展示个体画像而引入可识别个人信息。

## 6. 页面交互与联动矩阵

| 操作 | 总览页结果 | 流失分析页结果 |
|---|---|---|
| 选择全部游戏 | KPI、CCU、舆情排行、情感、地图恢复全样本 | 所有可汇总数据按正确分子/分母聚合 |
| 选择单款游戏 | 所有面板切换到该 appid | 所有 KPI、图表、主题和证据切换到该 appid |

| 点击地球语言市场 | 打开市场详情；可用时联动语言过滤 | 若数据支持语言过滤，可应用相同过滤；否则说明不可用 |
| 点击预警 | 展开规则、当前值、基线、样本量、来源 | 定位到相关情感/主题分析 |

| 点击数据来源 | 展示源文件、更新时间、覆盖范围、状态 | 同左 |

跨页状态可以使用 URL query 参数：
- `?appid=1203220`
- `?range=7d`
- `?topic=performance`

不得依赖浏览器 localStorage 保存唯一筛选状态；URL 应可分享、可刷新恢复。

- 主强调：青色；

- 风险色：红/橙/绿；
- 数字使用等宽字体；
- 面板边框与辉光克制，保证数据优先。

### 7.2 数据可读性要求

- 所有图表必须有单位。
- 轴范围不能为了视觉冲击误导变化幅度。
- 百分比默认 0–100%，若展示差值则单位明确为 pp。
- tooltip 至少显示日期、值、样本量。
- 图表无数据时显示空态组件，不显示空白坐标轴。
- 对低样本数据使用标记或提示，不用高饱和红色直接制造危机感。
- 不以动画模拟数据实时跳动；只在新数据加载完成时做轻量过渡。
- 保持响应式，窄屏时三栏转单栏，不能让 KPI 数字溢出。

### 7.3 建议图表类型

| 模块 | 图表 | X 轴 | Y 轴 | 备注 |
|---|---|---|---|---|
| CCU 趋势 | 多系列折线 | 真实时间 | 同时在线人数 | 不等间隔时间轴 |
| CCU 指数 | 多系列折线 | 真实时间 | 相对窗口均值指数 | 只比较节奏 |
| 舆情风险排行 | 横向条形/列表 | 游戏 | 风险指数 | 状态优先排序 |
| 情感对照 | 多系列折线 | 自然日 | 比例 % | Steam 与模型分开 |
| 预警 | 事件列表 | 时间 | — | 规则证据展开 |
| 语言市场 | 3D 点位 | 经纬度 | 点大小/颜色 | 代表点，不是用户位置 |
| 情感趋势 | 多系列折线+柱 | 自然日 | 比例/样本量 | 双坐标轴 |

## 8. API 与后端边界

本次优先使用 data 分支静态 JSON，不要求为了展示而新建一套重复 API。

如需后端 API，建议统一返回：

```json
{
  "meta": {
    "status": "ready",
    "source": "steam_reviews",
    "updated_at": "2026-11-24T04:51:15Z",
    "coverage": {
      "start": "2026-11-17",
      "end": "2026-11-24"
    },
    "sample_size": 300
  },
  "data": {}
}
```

接口建议（仅在前端静态文件不足以支持时实施）：

| API | 用途 | 参数 |
|---|---|---|
| `GET /api/dashboard/overview` | 总览所需聚合数据 | range |
| `GET /api/dashboard/games/{appid}/analysis` | 单游戏分析数据 | appid、start、end |
| `GET /api/dashboard/games/{appid}/reviews` | 评论证据分页 | topic、cursor、limit |
| `GET /api/dashboard/alerts` | 规则预警列表 | appid、range |
| `POST /api/ai/operations/insight` | 生成有证据引用的运营建议 | appid、evidence IDs |

接口要求：
- 返回结构化状态，不以 404 代表正常无数据。
- 业务无数据返回 200 + `status: empty`。
- 服务不可用返回合理 5xx 与可读错误码。
- 所有聚合都由后端或 adapter 统一计算，前端不重复定义口径。
- 评论分页不能一次性把整个 JSONL 下载进浏览器；若继续静态托管，建议由采集发布时生成按 appid/topic 索引的轻量 JSON。

### Phase E（2026-11-24，选做项）

Phase E 原本是「可后续考虑」的三类扩展数据源。按文档要求，先说明授权、稳定性、
采集频率与口径，再决定接不接。结论：

| 数据源 | 决定 | 理由 |
|---|---|---|
| Steam 官方公告（版本更新事件） | **已接入** | 数据已在本地知识库（103 篇公告，含 `publish_date` / `source_url`），零新增外部依赖；公开数据，随采集工作流更新 |
| SteamSpy（owners / 平均时长 / CCU 估算） | **未接入** | 第三方估算而非官方口径，且当前无稳定采集链路；若接入必须与 Steam 官方数据分列展示并标「第三方估算」 |
| Reddit / Twitch 社区热度 | **未接入** | 需要新的采集与清理流程、且频率与授权未确认；不得用外部热度指标冒充留存 |

**已接入部分的实现：**

- 后端：`list_documents` 增加 `sort` 参数（白名单 `created_at` / `publish_date`），
  `GET /api/knowledge/documents?source_type=announcement&sort=publish_date&app_id=…` 可用。
  默认排序不变，未知值回落到默认（测试已覆盖，不做字符串拼接）。
- 前端：分析页导航新增「公告时间线」按钮 → 弹层列出该游戏最近的官方公告
  （日期 + 标题 + 原文链接）。选择「全部游戏」时列全站最近 30 条。
- 口径：弹层底部常驻一句「时间先后只作参照，不能仅凭发布日与指标变化重合就断言因果」，
  这是文档对事件时间线的明确约束。

**为什么不做成图上的事件标记：** 情感/CCU 曲线是按天聚合的，把公告日期钉到折线上看起来
很唬人，但视觉上极易被读成因果。当前做法是「并列可查」，不制造视觉暗示。
